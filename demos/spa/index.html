架构解释 · Kernel 视角

下述架构对三域通用 — 采购案例、知识管理案例、企业合规案例共享同一底座.

① 整体架构

浏览器 → 应用演示接口 → 规则引擎
  → 底座 (实体 / 关系 / 权限 / 审计)
  → 数据库

应用层只读「业务结论 + 证据 + 出处」三件套, 不直接接触底层数据.

② Kernel 六层职责

  • 实体层: 把现实世界的对象（控制项、制度、报价单）作为有 ID 的实体沉淀.
  • 关系层: 实体之间的语义连接（控制项 -需要系统- 系统、制度 -要求角色- 角色）走时序 + 出处可追溯.
  • 权限层: 任何数据读取先过权限判断, 业务身份与系统身份严格区分.
  • 检索层: 单 store 内做关键词 / 向量 / 结构化 / 关系检索的组合, 不依赖外部搜索引擎.
  • 上下文组装: 按场景规范（Spec）把实体 / 关系 / 文档 / 结构化数据打包成业务上下文.
  • 决策与证据: 规则只读上下文, 产出条件评估 + 决策 + 同构证据行, 全程可追溯.

③ 权限模型 — 先判权, 再决策

数据访问前先做权限检查, 不靠模型自觉. 拒绝访问直接阻断, 不留「拒绝后判 0 行」的语义漏洞.

业务情形结论证据行
员工可访问制度 + 制度有效有据可答2
员工可访问 + 制度过期需提供有效版本0 (allowlist)
员工不可访问无权访问0

④ 确定性决策 + 证据链

同一份输入, 跑十次结果完全一致 — 规则不读系统时间, 不读 uuid, 不调用任何外部随机源.

每一行决策的每一步条件都附「通过 / 不通过 + 业务语言描述」, 留下可追溯的依据 — 不是只回结论.

知识管理案例：制度有效 且 员工具备角色 → 有据可答；任一失败 → 需提供有效版本.

⑤ 域包隔离 — 换域不换底座

应用层 (采购 / 知识管理 / 企业合规 — 三域共享)
       ↓ 只依赖
规则引擎 (上下文组装 / 决策与证据 / 权限前置)
       ↓
底座 (实体 / 关系 / 权限 / 时序 / 审计 — 零领域 import)

加一个新业务领域, 只需新增一个「域包」目录; 底座不改. 三个域包已上线 (采购 / 知识管理 / 企业合规), 第四个按需添加.

关键纪律

  • Permission Before Intelligence: 权限检查发生在数据访问层, 不靠模型自觉.
  • 确定性决策: 同一份输入, 跑十次结果完全一致 — 不读系统时间, 不读 uuid, 不调用任何外部随机源.
  • 业务语言呈现: 蓝图页不暴露内部字段, 客户看到的是结论 + 凭证 + 出处.
  • 三域共享同一底座: 加新业务只需新增域包, 引擎零改动.
