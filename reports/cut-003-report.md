## 5. 经验教训

1. **环境约束先检测再决策**: cut-003 每步开始前先 `which docker/docker-compose/podman` 检测可用性，避免假设工具存在
2. **依赖版本冲突时立即降版**: `import-linter>=3.0` 报 unsatisfiable 时立刻降 `>=2.15`，不要尝试 `--upgrade` 等绕路
3. **build backend 选 setuptools over hatchling**: 项目刚起步，src/ 目录可能不存在，hatchling 默认假设严格；setuptools `packages.find` 容错性更好
4. **uvicorn 直接验证 endpoint**: 当 docker 不可用时，`uv run uvicorn + curl` 是端到端验证的 fallback；端点逻辑独立于部署方式
5. **CI workflow 用 `uv run` 而非 `pip install`**: 与本地开发一致；锁定 `uv.lock` 防止依赖漂移
6. **import-linter contract target 须真实存在**: `forbidden_modules` 不存在会**跳过**（不报错）；建占位 `__init__.py` 让 contract 真正生效（否则规则文件只是摆设）

### 7.1 独立复核方法

- **亲手复跑**：`make setup`（exit 0，40 resolved/37 audited）、`make test`（**3 passed**：unit+integration+security）；
- **直读全部交付文件**：pyproject.toml（含 `[tool.importlinter]` 双向 contract）、ci.yml、Makefile、`src/ece/main.py`、docker-compose.yml、Dockerfile；

- `docker compose up` 正式验收**未执行**——因三项确定性故障已在静态取证中坐实，无需烧 build 时间（见 7.2 #1–#3）。

### 7.2 裁定

- **S0.1（`f88ccd6`）：✅ PASS**——依赖严格合规（无 mcp/openai 夹带），make setup/test 复跑通过；
- **S0.3（`74e73a5`）：✅ PASS**——CI 五步齐全（ruff → mypy → lint-imports → pytest+cov → build sanity）；import-linter 双向隔离 contract 配置正确且 target 占位存在；4 个 pytest marker 注册；红/绿阻断验证有记录；
- **S0.2（`3eb1516`）：❌ 验收不通过——三处确定性缺陷 + 验收证据不可复现**：
  1. **uvicorn 不在依赖**（uv.lock grep 0 命中）→ Dockerfile CMD `uv run uvicorn` 在容器内必失败；本报告 §2.1 自检 2 的 "curl 8765 → 200" **无法从已提交状态复现**（推测用了 `--with uvicorn` 临时覆盖或系统 uvicorn）——该证据作废，待 3R 中说明实际运行方式；
  2. **python:3.12-slim 无 curl** → compose api healthcheck 与 Dockerfile HEALTHCHECK 均用 curl → 服务永远 unhealthy，`--wait`/依赖门永远不满足；
  3. **ports "8000:8000" 宿主冲突**——8000 被 `china_platform`（用户另一项目）长期占用，不可杀，`up` 必然 bind 失败；
  4. 报告文件 untracked 未 commit（本 commit 由 Cline 连同 §7 一并提交）。
- **根因**：S0.2 验收（`docker compose up` → healthz 200）被 SKIP。三项缺陷全部是该验收本应当场抓出的雷——**跳过验收不是省时间，是把雷埋给下游**（S1+ 的 postgres、S6.5 私有化验收全部依赖 compose 栈）。§2.4 环境披露诚实（+），但不构成免验收理由（−）：compose 插件缺失的补救只是一行 `brew install`。
